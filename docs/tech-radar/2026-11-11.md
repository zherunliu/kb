## 01 · .NET 11：把业务状态写进类型，也减少日常工具开销

**2026-11-10 · 开发工具 / 编程语言 · 正式发布，STS 支持期为两年**

Microsoft 发布 .NET 11，包含 C# 15、运行时与 SDK 更新。SDK 默认启用 Native AOT CLI host，并让 MSBuild server 在命令调用之间保持就绪，以减少重复启动工作；并不是所有命令都因此脱离托管执行路径。.NET 11 属于标准期限支持（STS），.NET 10 仍是受支持的 LTS 选项，两者的区别在支持时长，而非质量或维护政策。[正式发布公告](https://devblogs.microsoft.com/dotnet/announcing-dotnet-11/)

C# 15 的联合类型可以声明一个值只属于若干候选类型之一，并对 `switch` 表达式进行穷尽性检查。例如查询结果可以明确分成“找到商品”和“未找到”，调用方能从类型看见需要处理的分支。封闭继承层次也能帮助编译器检查模式覆盖；内存安全规则的独立改进仍为预览功能。[语言特性与预览边界](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15)

**为什么值得关注：** 前端常用联合类型描述请求状态或组件属性，这种建模方式在后端语言中同样有价值。把有限结果写进接口，可以减少调用方靠注释猜测、用空值或异常混合表达业务结果的情况。

**Codex 建议：** 不熟悉 .NET 也可以先读联合类型示例，关注“接口怎样让遗漏分支更早暴露”。已有项目则应结合依赖兼容性、部署环境和支持周期评估迁移；编译器能检查已声明的分支，仍不能替你证明业务状态定义完整。工具链的性能改进也需要用自己的构建和测试流程衡量。

## 02 · Gemini 4 Carbon：从受限试用扩展到更广的付费访问

**2026-11-10 · AI / 开发平台 · 付费 API 开放，Ultra 产品入口滚动上线，Antigravity 的 /swarm 为预览**

Google 宣布扩大 Gemini 4 Carbon 的访问范围：付费开发者和企业可通过相关 API 使用，Google AI Ultra 用户的 Gemini、Antigravity 与搜索 AI Mode 入口陆续上线。此前 Carbon 已通过 Fairwind 向部分网络安全防守方提供，此次不是模型首次被披露。专门的网络安全访问与科研计划仍各有申请条件。[Google 原始公告与接入范围](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-carbon-now-available/)

Google 将 Carbon 定位于复杂、多步骤的工程和研究任务，并说明它会比 Argon 使用更多 token 进行探索与验证。同日预览的 `/swarm` 尝试让不同模型承担协调、实现和检查等角色。公告中的能力、成本与榜单结论来自 Google 汇总的评测，本文没有独立复现。

**为什么值得关注：** 更长的任务不只是多生成一些文本，还涉及选择工具、追踪中间状态、发现失败并重试。模型访问扩大后，开发者有机会检查这些能力能否在自己的仓库和数据中兑现，而不必只依赖演示案例。

**Codex 观察：** 可以优先看任务完成后的证据：代码是否通过检查、输出是否可追溯、失败后是否正确恢复。多 Agent 能拆分工作，也会增加协调与重复执行成本；单次 token 价格并不能直接说明整项任务更便宜。模型可调用、产品入口已为某个账户开通，以及 `/swarm` 已稳定可用，是三个需要分别确认的状态。

## 03 · NATS：毕业是成熟度里程碑，投递语义仍要逐项选择

**2026-11-10 · 开源 / 基础设施 · CNCF Graduated；消息与 JetStream 能力为既有功能**

CNCF 宣布 NATS 毕业，认可其生产采用、治理与维护成熟度。NATS 用于连接分布式应用、设备和 Agent，JetStream 在即时通信之上增加消息持久化等能力。此次是基金会项目阶段变化，不是消息服务当天首次发布；公告提及的 NATS Server 2.16 仍计划于 2027 年 3 月推出。[CNCF 毕业公告](https://www.cncf.io/announcements/2026/11/10/cncf-announces-nats-graduation-solidifying-a-production-ready-foundation-for-messaging-across-cloud-and-edge/)

官方文档区分了两条路径：Core NATS 将消息交给发布当时在线的订阅者，采用至多一次投递；JetStream 通过 stream 保存消息、consumer 跟踪消费进度，支持回放与至少一次投递。消费方未及时确认时可能发生重投，因此接入持久化并不自动保证业务动作只执行一次。[JetStream 概念与示例](https://docs.nats.io/concepts/jetstream)

**为什么值得关注：** 应用从同步请求走向后台任务、设备事件或 Agent 协作时，通信双方往往不会一直同时在线。持久化和消费进度能跨越这段时间差，但也把保留策略、重试与重复处理带进系统设计。

**Codex 建议：** 先确认业务是否需要离线补收、历史回放和失败重试，再选消息路径。毕业状态可以作为评估项目维护与治理的线索，不能代替容量测试、故障演练和幂等设计。尤其是“消息收到并确认”和“外部业务操作完成”之间，仍需要应用明确处理失败后的恢复方式。
