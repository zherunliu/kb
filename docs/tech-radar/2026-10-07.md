## 01 · GitHub：把有依赖的改动拆成可分别评审的小 PR

**2026-10-06 · 开发工具 / 协作 · 已正式上线，部分配套能力仍在分批开放**

GitHub 宣布堆叠拉取请求（stacked pull requests）正式可用，覆盖 github.com 全部套餐。它把相互依赖的 PR 组织起来，允许分别评审、一起合并。本次更新包括在符合条件的变基中保留审批，以及让一组堆叠 PR 作为单个合并组进入合并队列。[官方发布说明](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)

**为什么值得关注：** 例如一次改动包含“底层接口调整 → 调用方迁移 → 界面改造”，拆成三个 PR 更容易解释各自目的，但也需要维护它们的先后关系。堆叠 PR 将这种依赖显式呈现，有助于减少评审者在一个巨大差异中来回寻找上下文。

**Codex 建议：** 值得先读公告中的合并与变基规则。自动合并堆叠 PR 仍将在未来几周逐步开放，GitHub Enterprise Server 支持也属于后续版本计划，不能由“正式上线”推断所有入口今天都已具备。是否更高效，仍取决于团队怎样拆分改动和处理依赖。

## 02 · DNSSEC：根密钥即将轮换，先确认解析器信任了谁

**2026-10-06 · 网络 / 安全基础设施 · 新检查说明；密钥切换计划于 2026-10-11 进行**

Cloudflare 发布 DNS 根密钥轮换的准备说明，并介绍基于 RFC 8509 的就绪测试。IANA 的计划显示，KSK-2024 将于 10 月 11 日接替 KSK-2017 承担签名；截至本次检索，前者仍处于预发布状态。这是未来计划，尚不是已完成的切换。[Cloudflare 原始说明](https://blog.cloudflare.com/root-ksk-2024-rollover/) · [IANA 信任锚与轮换计划](https://www.iana.org/dnssec/files)

**为什么值得关注：** DNSSEC 验证需要一个预先信任的起点，也就是根信任锚。若启用验证的解析器没有信任新密钥，切换后可能把原本正常的 DNS 答复判为验证失败。网站本身没有故障，用户仍可能无法访问。

这里主要涉及 **DNSSEC 验证解析器的维护者**，多数网站运营者无需修改域名配置。此次更换密钥仍使用 RSA/SHA-256，并不代表 DNS 根已迁移到后量子算法。

**Codex 观察：** 原文值得看的细节是测试如何解释结果：解析器不支持 sentinel 协议时，结论可能只是“无法判断”，不能直接认定新密钥缺失。浏览器的安全 DNS 或 VPN 也可能改变实际被测试的路径；一次结果只对应当时使用的解析路径。

## 03 · 近期补读：Rust 1.99 补齐与 C 接口衔接的能力

**2026-10-01 · 编程语言 / 系统开发 · 稳定版**

Rust 1.99 稳定了使用 `C`、`C-unwind` ABI 定义可变参数函数的能力。Rust 此前已能调用外部定义的这类函数，现在也能用 Rust 实现它们。新版还稳定了从裸指针查询值的大小、对齐与布局的相关 API。[官方发布说明](https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/)

**为什么值得关注：** 既有系统和库往往暴露 C 接口，语言间协作要遵循调用约定。这项变化扩展了 Rust 可以直接实现的接口范围；可变参数的类型和数量仍需遵守接口约定，稳定化并不消除这些安全责任。

**Codex 建议：** 除新 API 外，也值得看公告对 `Box::leak` 的说明：官方更新了文档，建议避免先泄漏、再回收同一块内存的用法，转而考虑 `Box::into_raw` 等接口。这是使用建议的变化，不应写成已有代码在本版必然失效。阅读语言更新时，区分新能力、兼容性变化和推荐做法，往往比只看版本号更有价值。
