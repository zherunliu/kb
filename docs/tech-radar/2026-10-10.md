## 01 · Mellum2.1：把真实仓库任务带进模型训练

**2026-10-08 · AI / 开发工具 · 权重已发布，Apache 2.0 许可**

JetBrains 发布 Mellum2.1，沿用总参数 120 亿、每次激活约 25 亿参数的 MoE 架构，更新重点是后训练。官方模型卡介绍，软件工程训练让模型在真实仓库中使用 shell 和文件编辑工具，并以测试通过作为奖励依据。模型权重已在 Hugging Face 提供。[原始公告](https://blog.jetbrains.com/ai/2026/10/mellum2-1-gets-to-work-a-fast-open-model-for-coding-agents/) · [官方模型卡](https://huggingface.co/JetBrains/Mellum2.1-12B-A2.5B-Thinking)

**为什么值得关注：** 编程 Agent 需要在读取代码、执行命令和检查结果之间连续作出判断。把这类交互纳入训练，有机会改善“能写出一段代码，却难以完成一次仓库修改”的问题。开放权重也让开发者可以自行选择推理环境，观察模型与工具组合后的实际表现。

**Codex 观察：** 模型卡明确标注，评测结果由 JetBrains 自报。阅读时可以看任务环境、工具配置和采样条件，再判断结果能否用于比较。激活参数较少也不代表只需存放同等大小的权重；实际资源需求还受精度、上下文和并发影响。它是一个值得观察的自部署候选，本文没有验证本地运行成本或修复成功率。

## 02 · ONNX Runtime 1.31：模型部署接口逐步稳定

**2026-10-09 · AI 基础设施 / 开源运行时 · 正式发布**

ONNX Runtime 1.31.0 将模型包和 EPContext 数据接口提升为稳定的 C/C++ API。前者用于加载模型包、选择兼容的模型变体并创建会话；后者允许应用管理执行后端上下文数据的读写。新版还将 CoreML 接入基于设备的执行后端选择，支持通过 `PREFER_NPU` 选择 Apple Neural Engine。[官方发布说明](https://github.com/microsoft/onnxruntime/releases/tag/v1.31.0)

**为什么值得关注：** 模型进入应用后，除了推理速度，还涉及模型如何打包、适配哪种硬件，以及运行时数据存放在哪里。接口稳定让应用更容易围绕这些环节建立长期维护的部署流程。对跨平台应用来说，同一套上层调用怎样落到不同设备，也会影响交付复杂度。

**Codex 建议：** 已使用 ONNX Runtime 的项目，可以先读兼容性说明：原有实验性接口入口已被移除，需要迁移到稳定接口；核心运行时与插件的贡献算子定义也必须匹配。公告提醒，不匹配可能导致错误执行或崩溃，且插件注册时未必能发现。升级时，能加载插件和能正确运行模型需要分别验证。

## 03 · OSERA：让使用相同依赖的组织共同维护补丁

**2026-10-07 · 开源 / 软件供应链安全 · 已运营并交付首批补丁，完整平台仍在推进**

FINOS 宣布 OSERA 已进入运营阶段。联盟表示，已为 Spring 和 Java 生态中 50 多个常用开源项目交付带标准证明材料的安全更新，供成员使用；首个端到端平台版本仍计划在 11 月交付。这次新闻是运营与交付进展，修复标准的首个版本此前已发布。[基金会原始公告](https://www.linuxfoundation.org/press/major-banks-back-osera-to-deliver-industry-wide-remediation-standards-and-fixes-to-secure-open-source-software)

**为什么值得关注：** 多家组织使用相同依赖时，可能各自维护旧版本、重复回移同一个修复。共同出资与统一证据要求，有机会减少重复劳动，也让补丁使用者更清楚地知道它基于什么版本、修改来自哪里。这是开源协作从功能开发延伸到长期维护的一种实践。

**Codex 观察：** 最值得读的是公开的[修复标准目录](https://standards.osera.finos.org/)：它区分已批准的标准包、后续草案和仅观察的条目。不能把目录中出现的所有要求都视为已经强制执行。标准和源码开放，也不等于所有人都已获得成员服务；采用补丁时，仍需确认具体版本、来源与自身应用的兼容性。

## 今天值得继续看什么

对编程模型感兴趣，可以先读 **Mellum2.1 模型卡**，了解它如何训练和评测仓库任务。正在部署模型的读者，更值得直接查看 **ONNX Runtime 的兼容性说明**。想换一个角度看开源生态，则可以读 **OSERA 的标准目录**，观察一份补丁需要提供哪些信息，才能被其他组织放心接手。

这几条动态都涉及交付之后的工作：模型如何完成任务、运行时如何适配环境，以及依赖如何持续获得修复。它们的实际价值，需要在具体任务和维护过程中继续验证。
